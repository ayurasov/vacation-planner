# О документе

Программа и методика испытаний (ПМИ) определяет объект, цель, состав, порядок, условия и методы приёмочных испытаний программы «Планировщик отпусков» версии 1.0.0. По результатам испытаний кадровая служба заказчика подписывает демонстрацию сценариев приёмки, а служба информационной безопасности — чек-лист безопасности (техническое задание, раздел «Приёмка»). Документ подготовлен по истории бэклога E50-01: каждое требование и каждый сценарий технического задания проверяется хотя бы одним испытанием `ИСП-NN`, для которого указаны требование, роль, предусловия, данные, шаги, ожидаемый результат и автоматический тест, подтверждающий то же поведение в CI.

Структура следует практике ГОСТ 34.603-92 «Виды испытаний автоматизированных систем» и ГОСТ 19.301-2000 «Программа и методика испытаний. Требования к содержанию и оформлению» в сокращённом виде: сохранены объект, цель, требования, состав и порядок, условия, методы и критерии; сведения о технических средствах и подготовке объекта объединены в разделе «Условия проведения». Результаты записываются в «Протокол приёмочных испытаний» (`docs/acceptance/protocol.md`).

# Объект испытаний

Объект — «Планировщик отпусков» 1.0.0: корпоративная система планирования и согласования ежегодных отпусков по нормам ТК РФ для кадровой службы, руководителей и сотрудников. Клиент-серверное веб-приложение поставляется для установки на серверы заказчика (on-premise) в контейнерах Docker Compose.

| Компонент | Состав | Где в поставке |
|---|---|---|
| Сервер API | Node.js 22, NestJS 11, Prisma 6; REST API v1, поток событий SSE, плановые задачи; контейнер `server` | `server/`, `server/Dockerfile` |
| Веб-клиент | Vue 3 SPA за nginx с заголовками безопасности; контейнер `web` | `web/`, `web/Dockerfile`, `web/nginx.conf` |
| СУБД | PostgreSQL 17; контейнер `postgres`; миграции применяются при старте `server` | `docker-compose.yml`, `server/prisma/migrations/` |
| Резервное копирование | Контейнер `backup` (`pg_dump` по расписанию) | `docker-compose.yml` |
| Необязательные компоненты | Мониторинг (профиль `monitoring`), реплика PostgreSQL и архив WAL | `deploy/`, `docker-compose.replica.yml` |
| Контракт API | OpenAPI 3.1, 83 операции | `contracts/openapi-vacation-api-v1.yaml` |
| Состав компонентов | SBOM CycloneDX, отчёт о лицензиях | `sbom/`, `docs/sbom/` |
| Документация | Спецификации, руководства, документы для реестра, ADR | `docs/` |

# Цель испытаний

1. Подтвердить, что «Планировщик отпусков» 1.0.0 соответствует техническому заданию: функциональным требованиям FR-1…FR-18, сценариям приёмки СП-1…СП-15, нефункциональным требованиям, требованиям к безопасности, поставке и приёмке.
2. Провести демонстрацию сценариев приёмки для подписи кадровой службы (ТЗ, «Приёмка», п. 2) и проверку чек-листа безопасности для подписи службы ИБ (п. 4).
3. Подтвердить показатели производительности на конфигурации, рекомендованной отчётом сайзинга, и порядок установки, обновления, резервного копирования и восстановления по эксплуатационной документации.
4. Выявить расхождения программы и документации с ТЗ, оформить их замечаниями с решением в бэклоге и принять решение о приёмке программы в эксплуатацию.

## Порядок проведения

1. Э1 выполняется первым: без зелёных конвейеров CI на теге `v1.0.0` (ИСП-01) остальные этапы не начинаются. Автоматический тест, указанный в испытании, считается подтверждением, если он выполнен в CI на коммите тега и пройден; ссылка на прогон записывается в протокол.
2. Э2–Э4 выполняются на демонстрационном стенде (ИСП-02) по возрастанию номеров: некоторые испытания используют данные предыдущих (например, ИСП-12 использует заявку ИСП-09, ИСП-45 — сотрудника ИСП-44). Перед Э2 снимается внеочередная резервная копия (ИСП-62, шаг 2): при необходимости стенд возвращается в исходное состояние восстановлением.
3. Испытания с двумя пользователями выполняются в двух разных браузерах либо в обычном и приватном окне.
4. Э5 выполняется на отдельном стенде нагрузки с отдельной базой `vacation_load`; демонстрационный стенд и рабочие базы не используются.
5. Э6 выполняется на отдельном сервере или виртуальной машине (ИСП-60, ИСП-61, ИСП-63) и на демонстрационном стенде (ИСП-62, ИСП-64).
6. Э7 выполняется параллельно с остальными этапами; расхождения документации, найденные в любом испытании, записываются в ИСП-66.
7. По каждому испытанию в протокол заносится результат «соответствует», «не соответствует» или «не проверялось» (с причиной) и номера замечаний.

## Обязательные и необязательные испытания

Необязательные испытания проводятся, если заказчик использует соответствующую возможность; результат «не проверялось» по ним не препятствует приёмке.

| Испытание | Условие проведения |
|---|---|
| ИСП-04. Единый вход OpenID Connect | В организации есть провайдер OpenID Connect (Keycloak, ADFS, Blitz Identity Provider и др.) |
| ИСП-24. Письма и еженедельная сводка | Есть SMTP-релей организации или тестовый почтовый сервер |
| ИСП-59. Пиковые операции, запас и длительная работа | Требуется заказчиком сверх ТЗ; пороги — по отчёту сайзинга |
| ИСП-63. Реплика, архив WAL и переключение | Заказчик эксплуатирует стенд с репликой (RPO 15 минут) |

# Методика испытаний

Каждое испытание оформлено карточкой и таблицей шагов. В карточке указаны: требования ТЗ, функции, роль и учётные записи, предусловия, данные, автоматический тест (файл и название теста `describe`/`it`/`test`) и номера соответствующих проверок «Инструкции для эксперта». Если автоматического теста нет, записано «ручная проверка». Испытание считается пройденным («соответствует»), если на каждом шаге получен ожидаемый результат; отличие на любом шаге оформляется замечанием (раздел «Порядок оформления замечаний»).

Для тестов с параметрами (`server/test/rights-matrix.e2e.test.ts`) название случая строится как «`<operationId>` — `<что проверяется>`», например «updateSettings — изменить правила». Шаги с пометкой «(ИТ)» выполняет член комиссии от ИТ: они требуют доступа к серверу или вызова API.

# Критерии приёмки

Программа считается выдержавшей приёмочные испытания, если одновременно выполнены условия:

1. Все обязательные испытания имеют результат «соответствует» либо «не соответствует» только с замечаниями классов «Н» и «Д», по которым принято решение.
2. Открытых замечаний класса «К» нет.
3. По каждому замечанию класса «З» принято решение со сроком устранения до ввода в промышленную эксплуатацию и согласием председателя комиссии; иначе программа принимается в опытную эксплуатацию, а не в промышленную.
4. Оба конвейера CI пройдены на коммите тега `v1.0.0` (ИСП-01); тест матрицы прав пройден (ИСП-40).
5. Показатели этапа Э5 выполнены: p95 чтения ≤ 300 мс, p95 записи ≤ 500 мс, 0 ошибок; остальные показатели — по отчёту сайзинга.
6. Отчёт о лицензиях не содержит copyleft и неопределённых лицензий (ИСП-53).
7. Чек-лист безопасности подписан службой ИБ (ИСП-55); демонстрация сценариев приёмки СП-1…СП-15 подписана кадровой службой.
8. Необязательные испытания (ИСП-04, ИСП-24, ИСП-59, ИСП-63) могут иметь результат «не проверялось» с указанием причины; доступность (ИСП-64, шаг 6) — «не проверялось» до опытной эксплуатации.

Испытание с результатом «не проверялось» без допустимой причины считается непроведённым: приёмка возможна после его проведения.

## Порядок

1. Замечание записывается в протокол в ходе испытания: номер `ЗП-NN` (сквозной), испытание и шаг, фактический результат, ожидаемый результат по ПМИ, класс, доказательство (снимок экрана, ответ API, идентификатор запроса `X-Request-Id` из сообщения об ошибке).
2. Класс предлагает член комиссии, выявивший замечание; окончательно его утверждает комиссия при подведении итогов.
3. По каждому замечанию комиссия принимает одно из решений: «устранить до подписания акта», «устранить до ввода в промышленную эксплуатацию» (версия 1.0.x), «перенести в версию 1.1.0», «исправить документацию», «не является дефектом» (с обоснованием).
4. Правообладатель в течение `[заполняет заказчик]` рабочих дней переносит замечания в бэклог `docs/specs/03-backlog.md` — раздел «Замечания приёмки 1.0.0» в составе версии 1.0.0 (изменения `docs/specs/` проходят ревью владельца по `CODEOWNERS`). Формат строки:

   | ID | ИСП | Замечание | Класс | Решение | Версия и срок | История или PR | Статус |
   |---|---|---|---|---|---|---|---|
   | ЗП-01 | ИСП-NN, шаг N | Фактический результат и ожидаемый по ПМИ | К/З/Н/Д/П | Решение комиссии | 1.0.x, дата | `story/<id>` или ссылка на PR | открыто / устранено / подтверждено |
