# Нагрузочная проверка v0.5.0

Отчёт по истории E40-02: «Планировщик отпусков» выдерживает 5000 пользователей в базе и 500 одновременно работающих — p95 чтения не больше 300 мс, записи не больше 500 мс, без ошибок 5xx — на протяжении 15 минут.

**Итог:** требование выполнено. Итоговый прогон в режиме клиента v0.5.0 (поток событий): 500 пользователей, 16 минут, 200 777 запросов, **0 ошибок**, **p95 чтения 190 мс, записи 285 мс**. В режиме опроса (клиент без потока событий — худший случай для сервера): 192 322 запроса, 0 ошибок, p95 чтения 130 мс, записи 166 мс. Та же нагрузка на v0.4.0 давала p95 чтения 9,2 с, записи 14,4 с и 1 % ошибок.

Прогоны нашли три дефекта, которые не ловили тесты: взаимную блокировку при подаче заявок, срок refresh-cookie 15 минут вместо 30 дней и лишний разбор ключа JWT на каждом запросе. Все исправлены в v0.5.0. Рост задержек в конце одного из прогонов разобран отдельно (раздел «Хвост задержек»): это замедление стенда, а не приложения, — контрольный повтор той же сборки его не дал.

# Стенд и данные

| Параметр | Значение |
|---|---|
| Узел | 4 vCPU, 16 ГБ ОЗУ — один на всё: API, PostgreSQL и генератор нагрузки |
| API | Сборка `server/dist`, `WEB_CONCURRENCY=3` (одно ядро остаётся PostgreSQL и генератору), пул 10 соединений на процесс |
| PostgreSQL | 16, настройки по умолчанию (`shared_buffers` 128 МБ) |
| Данные | `npm run db:seed:load`: 5000 сотрудников, 152 отдела с руководителями, 25 539 отпусков, 3075 графиков работы |
| Генератор | `tools/load/run.mjs` без зависимостей (Node 22, fetch) |

Стенд намеренно скромнее рабочего: API, база и генератор делят четыре ядра. На выделенных узлах (документ 1, «Масштабирование») запас больше.

# Сценарий

Каждый виртуальный пользователь входит под своим логином со своего адреса (`X-Forwarded-For`, лимит входа считается по адресу), затем в цикле выбирает действие по весам и «думает» 1,5–4,5 с. Пользователи подключаются равномерно за 60 секунд и работают 15 минут.

| Действие | Вес | Запросы |
|---|---|---|
| График своего отдела за год | 30 | `GET /schedule?dept=…` с `If-None-Match` |
| Мой отпуск | 20 | `GET /employees/{id}/balance`, `GET /vacation-requests?scope=mine` |
| Колокольчик (только в режиме опроса) | 15 | `GET /notifications?unread=true` |
| Команда сегодня | 10 | `GET /analytics/team` |
| Подать и отменить заявку | 6 | `POST /vacation-requests`, `DELETE /vacation-requests/{id}` |
| Заявки подчинённых | 6 | `GET /vacation-requests?scope=subordinates&status=pending` |
| Аналитика года | 5 | `GET /analytics/overview` |
| График организации | 4 | `GET /schedule` без фильтра — 5000 сотрудников |
| Подбор дат | 4 | `GET /analytics/suggestions` |

Генератор ведёт себя как браузер: хранит `ETag` графика, обновляет access-токен по refresh-cookie при `401` и не отправляет cookie после её `Expires`. В режиме `--sse` каждый пользователь держит поток событий (вкладка), колокольчик перечитывается по событию `notifications`, а график — по событию `data`, не чаще раза в минуту и у трети пользователей («вкладка на экране»). Отказы `409` (пересечение с собственным отпуском) — правило, а не сбой; они считаются отдельно. Ошибка — любой иной ответ не 2xx/304 или обрыв.

# Найденные дефекты

| Дефект | Как проявился | Исправление |
|---|---|---|
| Взаимная блокировка при одновременной подаче заявок сотрудником и его руководителем | Один ответ 500 на 9 165 подач (`40P01 deadlock detected`) | Блокировки `FOR NO KEY UPDATE`; счётчик версии данных — отложенным триггером при фиксации (миграция `data_version_on_commit`); тесты |
| Refresh-cookie жила 15 минут вместо 30 дней | Найден при разборе обновления токенов: браузер удалял cookie вместе с истечением access-токена, сотрудника через 15 минут работы выбрасывало на вход | Cookie по сроку refresh-токена; тесты на вход, обновление и единый вход; генератор учитывает `Expires` |
| Ключ JWT разбирался на каждом запросе | Профиль процессора: 2 % времени — `createPublicKey` с исключением | Ключ создаётся один раз; алгоритм ограничен HS256 (тест отклоняет HS512 и `none`) |
| Генератор не обновлял токен | 5 997 ложных `401` после 15-й минуты первого прогона | Обновление по refresh-cookie, как в клиенте |

# Хвост задержек

В одном из пяти 16-минутных прогонов — опрос на сборке до исправления ключа JWT — в последние две минуты p95 на сервере вырос до 0,9 с на чтение и 3,3 с на запись. Контрольный повтор той же сборки с тем же генератором на том же стенде хвоста не дал; итоговая сборка — тоже, в обоих режимах клиента.

| Прогон | Минута 14 | Минута 15 | Минута 16 | Процессор API: минуты 2–14 → 16 |
|---|---|---|---|---|
| Опрос, до исправления ключа JWT | 122 / 228 мс | 223 / 539 мс | **932 / 3 329 мс** | 1,93 → **2,37** ядра |
| Та же сборка и генератор, контрольный повтор | 74 / 110 мс | 48 / 87 мс | 59 / 90 мс | 1,70 → 1,59 ядра |
| Опрос, итоговая сборка | 62 / 97 мс | 49 / 80 мс | 50 / 93 мс | 1,83 → 1,57 ядра |
| Поток событий, после исправления ключа JWT | 98 / 188 мс | 96 / 198 мс | 95 / 194 мс | 1,95 → 1,75 ядра |

В ячейках — p95 чтения / записи на сервере.

**Что произошло.** На 15-й минуте процессор API вырос с 1,9 до 2,4 ядра, а запросов за минуту обработано на четверть меньше (8 490 чтений вместо ~11 200): та же работа стала стоить больше процессорного времени. Цикл событий Node.js запаздывал до 1,15 с (p99 — 0,3 с), интерактивные транзакции дольше оставались открытыми — 11–13 соединений «idle in transaction» вместо 0–3, — и записи ждали блокировок друг друга. Поэтому запись пострадала сильнее чтения: 3,3 с против 0,9 с.

**Почему это стенд, а не приложение.**

- Контрольный повтор той же сборки хвоста не дал, и весь прогон обошёлся на 12 % дешевле по процессору: 1,70 ядра против 1,93 при том же числе запросов. Значит, в момент первого прогона медленнее был сам стенд. Узел — виртуальная машина с соседями; гипервизор отнимает у неё в среднем 2,5 % времени (steal), и эта доля неравномерна.
- Первое подозрение — истечение access-токенов: на 15-й минуте истекают токены всех 500 пользователей, вошедших в первую минуту. Но волна обновлений проходит незаметно: в контрольном повторе обновление токена — p50 12 мс, p95 73 мс, процессор не растёт. В целевых экспериментах с волной на 2-й минуте p95 записи не превышал 268 мс на итоговой сборке и 888 мс со старым разбором ключа JWT.
- Состояние базы со временем не накапливается: в журнале PostgreSQL за прогоны — только автоочистка и сбор статистики, без взаимных блокировок и ошибок; память процессов колеблется в одних пределах. Задержки итоговой сборки за 16 минут не растут, а снижаются: p95 записи — с 211 до 93 мс.

**Что из этого следует для эксплуатации.** Механизм усиления реален: при нехватке процессора первыми страдают записи — транзакции ждут друг друга, пока цикл событий занят. Для 500 одновременных пользователей нужен запас процессора; на стенде его съедали генератор и PostgreSQL на тех же четырёх ядрах. На рабочих узлах (документ 1, «Масштабирование») API и PostgreSQL разнесены. Признаки того же состояния ловят оповещения `VacationEventLoopLag` (p99 цикла событий выше 0,2 с) и `VacationIdleInTransaction` (больше 5 соединений «idle in transaction»); в разобранном случае оба порога были превышены.

# Как повторить

```bash
cd server
DATABASE_URL=postgresql://vacation:vacation@localhost:5432/vacation_load npx prisma migrate deploy
DATABASE_URL=postgresql://vacation:vacation@localhost:5432/vacation_load npm run db:seed:load
npm run build
DATABASE_URL=postgresql://vacation:vacation@localhost:5432/vacation_load JWT_SECRET=<32+ символа> \
  PORT=8097 WEB_CONCURRENCY=3 node dist/main.js
# в другом терминале
node ../tools/load/run.mjs --url http://localhost:8097 --users 500 --ramp 60 --duration 900 --sse --out result.json
```

Без `--sse` — режим опроса. Снимки `/metrics` раз в 15 секунд во время прогона дают перцентили по минутам и ресурсы. Скрипт наполнения отказывается работать с БД, в имени которой нет `load`.
