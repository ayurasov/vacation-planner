# О документе

Документ — план развития «Планировщика отпусков» по версиям и бэклог с критериями приёмки. Каждая история — законченный объём работы, который разработчик или ИИ-ассистент выполняет в ветке `story/<id>` и который проверяется ревью за 30–60 минут. Для выполненных историй указаны тесты, подтверждающие критерии; бэклог переносится в трекер один к одному.

| Связанный документ | Что в нём |
|---|---|
| 0 — Ревизия функциональности | Откуда взялись истории: состояние as-is и to-be |
| 1 — Описание архитектуры | Компоненты, на которые ссылаются истории |
| 2 — Спецификация API | Операции, коды ошибок и права |
| 6 — Правила разработки с ИИ | Как история передаётся ассистенту |
| 7 — Стенды, CI/CD и выпуск | Ветки, конвейеры и порядок выпуска |

# Правила бэклога

| Обозначение | Значение |
|---|---|
| `TL` | Технический лидер, архитектор |
| `BE`, `FE` | Разработчик сервера, клиента |
| `QA` | Инженер по тестированию |
| `DO` | Инженер эксплуатации |
| Оц. | Идеальные человеко-дни с учётом генерации кода ИИ-ассистентом |
| Ревью | `да` — обязательное ревью технического лидера (`auth/`, миграции, контракт, права, зависимости) |

**Готовность к работе:** есть ссылка на раздел документов 1–2 и операцию контракта; критерии проверяемы; зависимости закрыты или заменены заглушками; для историй с ревью назначен ревьюер.

**Закрытие:** критерии покрыты автотестами; оба конвейера CI зелёные; ревью пройдено; документы, `CHANGELOG.md` и при необходимости контракт обновлены в том же PR.

# Версия 0.6.0 — готовность к приёмке

Приёмка v1.0.0 — подпись кадровой службы и ИБ. Без этой версии ей мешают пробелы: в системе нет утверждённого графика и формы Т-7, сотрудник не получает извещения о начале отпуска (ТК РФ, ст. 123), согласование останавливается, пока руководитель сам в отпуске, а ИБ не видит входов, не управляет сеансами и не может потребовать смены одноразового пароля.

# Версия 1.0.0 — приёмка и подача в реестр

Первый выпуск для эксплуатации. Его принимают кадровая служба (сценарии технического задания) и служба ИБ (чек-лист документа 1 и проверка на проникновение), а правообладатель подаёт его в единый реестр российских программ (постановление Правительства РФ № 1236). Ориентир для документов — комплект «По Делу» (todo-planner): девять документов для реестра в Markdown, DOCX и PDF с чек-листом готовности, инструкцией для эксперта и трассировкой функций.

Отдельный эпик — подтверждение и отладка для типовой организации на 1000–2000 сотрудников: не предельный прогон на 5000 (v0.5.0), а модель рабочего дня с пиками, минимальная конфигурация сервера, длительная работа, рост данных за годы и отказы под нагрузкой.

Найдено и исправлено попутно: самооценка ИБ нашла 14 недостатков (`docs/security/assessment-v1.0.0.md`), из них два высокой важности — известный секрет подписи токенов по умолчанию в `docker-compose.yml` при приёме токенов без сеанса и порт PostgreSQL на всех интерфейсах узла с паролем из репозитория; карточки коллег отдавали нормы дней и табельные номера и логины любому вошедшему; Prisma, Scarf, npm и Swagger UI обращались за пределы контура при сборке и старте. Под перегрузкой и при отказах нашлись три ошибки: новая вкладка получала ложное завершение сеанса, `503` при обновлении токена выводил сотрудника на экран входа, а остановка API ждала открытые потоки событий до таймаута (`docs/performance/report-v1.0.0.md`). При подготовке регламентов: у сервисов не было политики перезапуска — после перезагрузки узла стенд оставался остановленным; `DB_POOL_SIZE`, `TRUST_PROXY` и `EVENTS_POLL_MS` из `.env` не доходили до сервера; архивирование WAL застревало после сбоя на уже скопированном сегменте; конвейер CI не запускался на ветке `v1.0.0`; пять ADR описывали Express и SQLite вместо NestJS и PostgreSQL.

Порядок: модель дерева и правило руководителя (E70-01, E70-02) — до обмена: форматы «По Делу» опираются на путь подразделения и руководителя по структуре; руководство в приложении (E71) — параллельно, отдельной веткой; ревизия интерфейса (E72) — в начале и в конце выпуска.

Найдено попутно: сотрудники отдела без явного руководителя попадали в очередь руководителя отдела, но не считались его подчинёнными — руководитель не видел их карточек и заявок в «Подчинённых»; с v1.1.0 подчинённые и очередь считаются одним правилом. Синхронизация с AD отложена до v1.2.0: она требует зависимости LDAP (запись в `docs/decisions.md` и SBOM).

# Критический путь и риски

v0.4.0: импорт (E30) открывает переход с кадровых таблиц; единый вход (E31) — условие пилота на 1000 пользователей. v0.5.0: метрики (E40-01) нужны до нагрузочного прогона (E40-02), а вынос лимита входа (E40-05) — до запуска второго экземпляра; оба условия выполнены. v0.6.0: утверждение графика (E60-02) должно быть готово до конца ноября — кадровой службе нужен месяц на кампанию и две недели до нового года (ТК РФ, ст. 123). v1.0.0: сайзинг (E51-02) и пики (E51-03) — до инструкции для эксперта и руководства по развёртыванию; сведения правообладателя (E52-01) и внешний тест на проникновение (E50-02) зависят от действий вне репозитория.
