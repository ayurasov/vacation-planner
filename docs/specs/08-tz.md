# Техническое задание: корпоративный планировщик отпусков, этап 1

| Параметр | Значение |
|---|---|
| Документ | ТЗ этапа 1 (документ 8 комплекта) |
| Версия | 1.0 |
| Дата | 27.10.2026 |
| Статус | На согласовании |
| Заказчик | HR-служба |
| Исполнитель | Команда разработки (с ИИ-ассистентами) |

## 1. Общие сведения

Система «Планировщик отпусков» — внутренний инструмент планирования и согласования отпусков компании до 500 сотрудников. Этап 1 переводит работающий прототип в корпоративный инструмент: серверная логика, безопасность, многопользовательская работа без конфликтов, аудит.

## 2. Назначение и цели

| Цель | Показатель |
|---|---|
| Потери данных при одновременной работе | 0 инцидентов за этап |
| Актуальность очереди согласования | без перезагрузки, задержка ≤ 30 с |
| Безопасность | Пароли в хешах, API авторизован, XSS отсутствует — приёмка ИБ |
| Готовность к 500 пользователям | Нагрузочный прогон E11-02 пройден |
| Аудит | Каждое изменение с актором и «до/после» |

## 3. Текущее состояние

Прототип (этап 0): SPA + Express/SQLite, бизнес-логика на клиенте, снимок состояния `PUT /api/state`, пароли открытым текстом, год зашит в код. Полная ревизия — документ 0.

## 4. Границы системы

Входит: заявки, согласование, график, балансы, справочники, режимы офис/удалёнка, аудит, уведомления, выгрузки. Не входит (этап 1): больничные, интеграция с 1С/ЗУП, SSO, email, мобильное приложение, мультиорганизационность.

## 5. Роли

| Роль | Описание |
|---|---|
| Сотрудник | Свои заявки и профиль, просмотр графика организации |
| Руководитель | + согласование подчинённых, оформление за них, режимы их работы, панели |
| Администратор | + все заявки, сотрудники, справочники, настройки, аудит, выгрузки |

## 6. Функциональные требования

FR-1..FR-10 соответствуют Ф1–Ф10 документа 1 (раздел 3.1) без изменений; детализация — документы 2 и 3. Ключевые сценарии приёмки:

1. Сотрудник подаёт заявку → руководитель видит её в очереди ≤ 30 с → согласовывает → сотрудник получает уведомление, график обновляется.
2. Два сотрудника одновременно подают/правят разные заявки → обе применяются, ни одна не теряется.
3. Перенос одобренного отпуска → на согласовании, прежние даты до решения; отклонение → откат дат.
4. Подача сверх остатка → блокировка (политика) с понятным текстом.
5. Удаление последнего администратора / отдела с сотрудниками → отказ с ошибкой из каталога.
6. Любое действие → запись в аудите с актором и изменениями.
7. Пароль нигде не отображается и не выгружается; XSS-проба (имя с `<img onerror>`) безопасна.

## 7. Нефункциональные требования

Раздел 3.2 документа 1: 500 пользователей / 50 одновременных; p95 ≤ 300 мс чтение; доступность 99 % в рабочие часы; RPO/RTO 24 ч/1 ч; TLS за Nginx; журналы без персональных секретов.

## 8. Архитектура

Модульный монолит Node.js/Express/SQLite; доменный слой; REST API v1 по контракту; JWT-аутентификация; фронтенд ES-модули. Полностью — документ 1.

## 9. Модель данных

Реляционная схема документа 4; миграция из snapshot-формата конвертером с отчётом сверки и нулевым расхождением (E10-01).

## 10. Миграция данных

Рабочая БД прототипа: 131 сотрудник, заявки, справочники. План: копия БД → конвертер → сверка → сброс паролей на одноразовые → переключение. Откат — восстановление копии. Окно миграции — вне рабочих часов, 1 час.

## 11. Требования к совместимости

Браузеры: два последних major Chrome/Firefox/Edge/Safari. Данные прототипа сохраняются при миграции (кроме паролей — сброс по В1). Протокол `PUT /api/state` отключается после двухнедельного переходного периода (В4).

## 12. Этапы работ

8 недель по карте эпиков документа 3; демонстрации в конце недель 2/4/6/8.

## 13. Команда

TL (0,3), BE (1), FE (1), QA (0,5), DO (0,2) + ИИ-ассистенты по правилам документа 6.

## 14. Приёмка

1. Прогон E2E-сценариев E11-01 (15+ сценариев, CI).
2. Нагрузочный отчёт E11-02.
3. Демонстрация сценариев раздела 6 — подпись HR.
4. Чек-лист ИБ раздела 9 документа 1 — подпись ИБ.
5. Нулевые расхождения отчёта миграции.
6. Green CI на релизном теге.

## 15. Риски

| Риск | Вероятность | Влияние | Митигирование |
|---|---|---|---|
| E03 (жизненный цикл) сложнее оценки | средняя | сдвиг выпуска | ревью ТЛ каждую неделю, таблица состояний под тестами с первого дня |
| Миграция вскроет грязные данные прототипа | высокая | переделка E10 | конвертер с отчётом расхождений; прогон на копии заранее (неделя 6) |
| Сопротивление сбросу паролей | средняя | недовольство пользователей | одноразовые пароли + принудительная смена, письмо-инструкция |
| Нагрузка выше ожиданий SQLite | низкая | деградация p95 | замеры на этапе (E11-02), критерии перехода на PostgreSQL в ADR-004 |
