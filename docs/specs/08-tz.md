# О документе

Техническое задание на корпоративную систему «Планировщик отпусков»: назначение, границы, роли, функциональные и нефункциональные требования, требования к безопасности, поставке и приёмке. Задание выросло из исходного задания на этап 1 (переход от прототипа к корпоративному инструменту) и уточнено по итогам версий 0.1–0.3.

|---|---|
| Заказчик | Кадровая служба |
| Исполнитель | Команда разработки с ИИ-ассистентами (документ 6) |
| Правообладатель | Александр Юрасов |
| Целевой масштаб | 1000 пользователей при вводе, рост до 5000 |

# Назначение и цели

Система ведёт планирование и согласование ежегодных отпусков организации: график всей компании, заявки с согласованием руководителем, балансы дней по нормам Трудового кодекса, режим работы офис/удалёнка, аналитику пересечений внутри отделов и неизменяемый журнал изменений.

| Цель | Показатель |
|---|---|
| Ни одной потери данных при одновременной работе | 0 инцидентов; тесты гонок в CI |
| Правильный учёт дней | Праздники не входят в отпуск; лимит не обходится; расчёт совпадает с ручной проверкой кадровой службы |
| Руководитель видит риски отдела заранее | Конфликты выше порога и выводы доступны на год вперёд |
| Безопасность | Пароли только в хешах; права на сервере; нет XSS; аудит каждого изменения — приёмка ИБ |
| Масштаб | 5000 пользователей, 500 одновременных; p95 чтения ≤ 300 мс |

# Границы системы

**Входит:** заявки и их жизненный цикл, согласование, график отпусков, балансы и лимиты, производственный календарь, подбор дат, аналитика отдела, график работы, сотрудники и оргструктура, правила организации, уведомления в интерфейсе, выгрузки XLSX, журнал аудита, резервное копирование.

**Не входит в v1.0:** больничные и иные виды отсутствия, кадровые приказы и расчёт отпускных, несколько юрлиц в одном экземпляре, мобильное приложение (адаптивная вёрстка — входит).

**Интеграции (v0.4.0):** импорт из кадровой системы, единый вход OIDC/AD, почтовый релей.

# Функциональные требования

| ID | Требование |
|---|---|
| FR-1 | Вход по логину и паролю; сеанс продлевается автоматически; смена пароля завершает все сеансы |
| FR-2 | Заявка на отпуск с проверкой дат, пересечений со своими заявками и лимита по политике организации (жёсткая или мягкая) |
| FR-3 | Жизненный цикл: на согласовании → согласован / отклонён; перенос согласованного с сохранением прежних дат до решения; запрос удаления; отмена |
| FR-4 | Баланс: норма + перенос − согласовано − на согласовании; праздники не входят в дни отпуска (ТК РФ, ст. 120); признак части не короче 14 дней (ст. 125) |
| FR-5 | Согласование руководителем по оргструктуре с показом пересечений в отделе; причина отклонения обязательна |
| FR-6 | График отпусков организации на год: отделы, поиск, масштаб, праздники, нагрузка, конфликты, сравнение сотрудников, выгрузка |
| FR-7 | Аналитика отдела: доля в отпуске по месяцам, периоды конфликтов, выводы, распределение дней |
| FR-8 | Подбор до пяти окон отпуска с учётом нагрузки отдела, праздников и своих отпусков |
| FR-9 | График работы офис/удалёнка: недельный шаблон и разовые исключения; состав отдела на дату |
| FR-10 | Сотрудники, отделы, проекты; защита последнего администратора; удаление только пустого отдела |
| FR-11 | Производственный календарь по годам; правила организации (порог конфликта 20–80 %, политика лимита, норма дней) |
| FR-12 | Уведомления о заявках и решениях с непрочитанными |
| FR-13 | Выгрузка XLSX по области прав без логинов и паролей |
| FR-14 | Журнал аудита: автор, время, действие, объект, значения до и после; неизменяем из приложения |

# Сценарии приёмки

1. Сотрудник подаёт заявку → руководитель видит её в очереди и колокольчике → согласует → сотрудник получает уведомление, график и баланс обновлены.
2. Отпуск 1–14 мая с тремя праздниками расходует 11 дней отпуска.
3. Две пересекающиеся заявки, отправленные одновременно, — создаётся одна; два одновременных решения — применяется одно, второе получает «данные изменились».
4. Перенос согласованного отпуска → на согласовании; отклонение → прежние даты.
5. Заявка сверх доступного при жёсткой политике → отказ с понятным текстом; при мягкой — отправка с предупреждением.
6. Подбор дат не предлагает окна, где отдел превысит порог, и окна, пересекающиеся со своими отпусками.
7. Руководитель не видит аналитику чужого отдела; выгрузка руководителя без отдела содержит только его подчинённых.
8. Удаление последнего администратора и непустого отдела → отказ с кодом из каталога.
9. Любое изменение данных, включая график работы и правила, — запись в журнале аудита.
10. Пароль не отображается и не выгружается; имя `<img src=x onerror=alert(1)>` отображается текстом; CSP не нарушается.

| Область | Требование |
|---|---|
| Производительность | p95 чтения ≤ 300 мс, записи ≤ 500 мс при 500 одновременных пользователях из 5000 |
| Доступность | 99,5 % в рабочие часы; плановые работы вне рабочего времени |
| Сохранность | RPO 24 ч, RTO 1 ч при вводе; RPO 15 мин с репликой (v0.5.0); ежемесячная проверка восстановления |
| Совместимость | Две последние версии Chrome, Edge, Firefox, Safari; ширина от 360 px |
| Доступность интерфейса | Клавиатурная навигация, контраст текста не ниже WCAG AA, состояние не передаётся только цветом |
| Локализация | Русский язык; часовой пояс организации; формат дат ДД.ММ.ГГГГ |
| Эксплуатация | Docker Compose на Linux; работа в закрытом контуре без доступа в интернет |

# Требования к безопасности

1. Пароли — только scrypt-хеши; минимальная длина 8 символов; одноразовый пароль при создании и сбросе.
2. Access-токен 15 минут в памяти клиента; refresh — httpOnly-cookie с ротацией и отзывом.
3. Ограничение частоты входа по паре «адрес + логин» и по адресу; адрес клиента — из заголовка доверенного прокси.
4. Права проверяются на сервере для каждой операции; данные чужих отделов не уходят в браузер.
5. CSP без inline-скриптов, запрет встраивания во фреймы, заголовки `X-Content-Type-Options`, `Referrer-Policy`.
6. Секреты только в окружении; сервер не стартует со слабым `JWT_SECRET`.
7. Сторонние компоненты — только под разрешительными лицензиями (документ 11).

# Архитектура и данные

Клиент-серверное веб-приложение: SPA на Vue 3, REST API v1 на NestJS 11, PostgreSQL 17, поставка в контейнерах Docker за nginx. Описание — документ 1; протокол — документ 2 и контракт OpenAPI; модель данных — документ 4.

# Поставка и сопровождение

1. Исходный код, контракт OpenAPI, миграции, Docker-файлы и конвейеры CI.
2. Комплект документов в Markdown, PDF и DOCX: спецификации 00–11, руководства пользователя, администратора и по развёртыванию, история версий.

4. Версии `v0.x.y` в собственных ветках; `main` — только принятые версии с тегами.
