## 1. Резюме

Планировщик отпусков — внутренний инструмент компании на до 500 сотрудников: график отпусков, заявки с согласованием, балансы дней, режимы офис/удалёнка, справочники и аналитика. Сегодняшняя версия — работающий прототип: вся бизнес-логика исполняется в браузере, сервер лишь хранит один JSON-снимок состояния, который каждый клиент перезаписывает целиком.

Целевая архитектура — **модульный монолит с серверной доменной логикой**:

1. **Сервер — единственный источник истины.** Вся бизнес-логика (статусы заявок, балансы, права, конфликты) переносится с клиента в доменный слой сервера. Клиент становится тонким: отображение и ввод.
2. **Контракт прежде кода.** Публичный REST API v1 (`contracts/openapi-vacation-api-v1.yaml`) фиксируется до разработки и не меняется без ревью. Ошибки — RFC 9457.
3. **Один гранулярный API вместо снимка состояния.** Каждое действие — отдельная операция над ресурсом; снимок `PUT /api/state` выводится из эксплуатации.
4. **Аутентификация и авторизация на сервере.** Хешированные пароли, JWT-сессии, права проверяются на каждом эндпоинте; клиентские проверки остаются только как UX.
5. **Три этапа.** Этап 0 (завершён) — CI, тесты, контракт, модульная структура. Этап 1 (8 недель) — серверное ядро: аутентификация, заявки, балансы, справочники, аудит, новый фронтенд на том же стеке. Этап 2 (6 недель) — аналитика, отчёты, производительность, email-уведомления, производственный календарь. Этап 3 — интеграции (1С/ЗУП, SSO), по отдельному ТЗ.

Стек сознательно не меняется: Node.js 20+ (LTS), Express, SQLite (WAL) с подготовленной заменой на PostgreSQL, ванильный JS-фронтенд с поэтапным разбиением на ES-модули. Причина — небольшая команда, низкая нагрузка (~500 пользователей, десятки запросов в минуту) и стоимость миграции.

## 2. Цели и проблемы бизнеса

| Проблема сейчас | Цель | Как достигается |
|---|---|---|
| При одновременной работе пользователи перезаписывают данные друг друга | Никаких потерь данных при полной одновременной работе | Гранулярный API + транзакции SQLite |
| Пароли хранятся и передаются открытым текстом, API анонимен | Соответствие внутренним требованиям ИБ | Хеши, JWT, серверная авторизация, экранирование |
| Руководитель не видит новые заявки без перезагрузки | Заявки и очередь актуальны всегда | Серверные уведомления + polling (этап 1), SSE (этап 2) |
| Система привязана к 2026 году | Работа на скольжении лет | Производственный календарь по годам, перенос остатков |
| Остатки дней расходятся с фактом | Единый расчёт на сервере | Серверные балансы + enforced-лимиты |
| Нет истории «кто что сделал» | Аудит каждого изменения | Серверный журнал действий |
| Прототип нельзя отдать ИБ и эксплуатации | Поставляемый продукт: стенд, бэкапы, мониторинг | Docker, CI/CD, бэкапы, health-пробы |

## 4. Архитектурные принципы

1. **Сервер решает, клиент показывает.** Любое правило, влияющее на данные (права, статусы, лимиты, конфликты), исполняется на сервере. Дублирование на клиенте — только для отзывчивости UI.
2. **Контракт прежде кода.** API v1 зафиксирован в `contracts/`; изменения — через ревью и только добавляющие.
3. **Совместимость вперёд.** Клиент игнорирует неизвестные поля; сервер добавляет поля, не удаляет и не переименовывает существующие.
4. **Одна операция — одна транзакция.** Каждое изменение пишет данные и событие аудита в одной транзакции SQLite.
5. **Простота прежде инфраструктуры.** Один процесс, одна БД, файловая журнализация. Redis, брокеры, микросервисы — не вводятся, пока не исчерпан монолит (критерии — ADR-004).
6. **Фронтенд без сборки на этапе 1.** ES-модули без бандлера; сборка (Vite) — только когда появится реальная потребность.
7. **Изменения через журнал.** Ни одно изменение данных не происходит без записи в аудит.
8. **Идентификаторы выдаёт БД.** Последовательные, никаких `Date.now()`.

## 5. Ключевые архитектурные решения

| № | Решение | Альтернатива | Почему так |
|---|---|---|---|
| Р1 | Модульный монолит на Express | Микросервисы | 500 пользователей, один домен, малая команда; модули изолированы по каталогам и выделяются позже |
| Р2 | SQLite (WAL) как основная БД этапа 1 | Сразу PostgreSQL | Один файл, нулевое администрирование, достаточная производительность; DAL скрывает диалект, критерии перехода зафиксированы в ADR-004 |
| Р3 | Гранулярный REST API v1 | Частичная правка снимка state | Снимок не масштабируется на конкурентность и права; контракт v1 — точка отсчёта |
| Р4 | JWT (access 15 мин + refresh в httpOnly cookie) | Серверные сессии в БД | Отсутствие состояния на сервере; отзыв через короткий срок жизни и версию пароля |
| Р5 | Пароли: scrypt (N=16384) с солью | bcrypt, argon2id | Встроен в Node без зависимостей; достаточная стойкость для внутреннего инструмента |
| Р6 | Доменный слой `src/domain/` без Express | Логика в роутах | Тестируемость правил независимо от HTTP; роуты тонкие |
| Р7 | Аудит в той же транзакции, что и изменение | Асинхронные события | Гарантия непротиворечивости журнала; объём событий низкий |
| Р8 | Фронтенд: поэтапный перенос в ES-модули без смены стека | React/Vue с нуля | Сохранение 4,6 тыс. строк работающей логики; риски переписывания больше выигрыша |
| Р9 | Конфликты считает сервер при запросе графика | Расчёт на клиенте | Один алгоритм для всех клиентов, O(N×дни) один раз на сервере |
| Р10 | Производственный календарь — таблица по годам, правимая администратором | Захардкоженный список | Многолетность; переносы выходных меняются указами |
| Р11 | Этап 1 без Docker на рабочих машинах, Docker на стенде | Повсеместный Docker | Минимум барьера для разработчиков; воспроизводимость — в CI и на стенде |

## 6. Архитектура в нотации C4 (текстовое описание)

Полные диаграммы (Mermaid-исходники в `docs/specs/diagrams/`) рендерятся через mermaid.live или плагин VS Code.

### C1. Системный контекст

- **Сотрудник** (браузер) → *Планировщик отпусков* → графики и заявки.
- **Руководитель** (браузер) → согласование, панели.
- **Администратор** (браузер) → справочники, пользователи, настройки, аудит.
- **Обратный прокси (Nginx)** терминирует TLS и отдаёт статику/проксирует API (стенд).
- Этап 3: **кадровая система** (импорт сотрудников), **почтовый релей** (этап 2 — уведомления).

### C2. Контейнеры (целевые)

| Контейнер | Технология | Ответственность |
|---|---|---|
| SPA-клиент | Vanilla JS ES-модули | UI: график, формы, очереди; токен в памяти + refresh-cookie |
| API-сервер | Node.js 20, Express | REST v1, аутентификация, авторизация, статика клиента |
| Доменный слой | `src/domain/` | Правила: заявки, балансы, права, конфликты, календарь |
| БД | SQLite WAL (`data.db`) | Персональные данные, журналы; ежедневный бэкап |
| Nginx (стенд) | docker | TLS, сжатие, раздача статики, лимиты частоты |

### C3. Компоненты сервера

```text
src/
  app.js            сборка Express (роуты, middleware)
  server.js         точка входа
  db.js             соединение, схема, миграции
  auth/             JWT, пароли, middleware аутентификации
  domain/
    employees/      профиль, права, подчинение
    requests/       конечный автомат заявок, переносы, удаления
    balance/        расчёт балансов, политика лимитов
    schedule/       интервалы графика, режимы работы, конфликты
    directories/    отделы, проекты, группы
    calendar/       производственный календарь
    audit/          журнал изменений
    notify/         уведомления
  api/              HTTP-слой: валидация входа, маппинг ошибок RFC 9457
```

Правило зависимостей: `api/` → `domain/` → `db.js`. Домены не импортируют друг друга напрямую, кроме явных сервисов (`balance` использует `requests`-репозиторий только через интерфейс чтения).

## 7. Доменная модель

Подробные схемы — документ 4. Ключевые сущности:

- **Employee** — сотрудник: ФИО, должность, отдел (id), роль, админ-флаг, тип занятости, руководитель, проект, плановые дни, перенос.
- **VacationRequest** — заявка: сотрудник, даты, тип (vacation/maternity), статус, признак переноса/удаления, история.
- **Department / Project / Group** — справочники с руководителями и составом.
- **OrgSettings** — настройки организации: порог конфликта, часовой пояс, политика лимитов.
- **ProductionCalendar** — праздники и переносы по годам.
- **AuditEvent** — журнал: актор, действие, сущность, до/после.
- **Notification** — уведомление пользователя.

## 8. Состояния заявки

```text
                 ┌──────────(отмена автором)──────────┐
                 ▼                                    │
Создана ──► pending ──approve──► approved ──(перенос)──► pending [changeFrom]
   │           │                                  │
   │           └──reject──► rejected               └──(удаление)──► pending [pendingDeletion]
   │                                                        approve ──► удалена
   └──(авто-утверждение: админ или руководитель за подчинённого)──► approved
```

Инварианты (проверяет сервер):
1. Даты корректны: `start ≤ end`, обе в будущем (кроме действий администратора).
2. Период не пересекается с другими заявками того же сотрудника в статусах pending/approved — иначе 409.
3. Изменить/отменить pending-заявку может автор, администратор или согласующий.
4. Одобренный отпуск меняется только через новую заявку-перенос (старая сохраняется до решения).
5. Баланс: сумма approved+pending не может превышать entitlement + допустимый перерасход (настройка; по умолчанию 0).

## 9. Безопасность

1. Пароли — scrypt с уникальной солью; при первой миграции все пароли сбрасываются на одноразовые (политика этапа 1).
2. Access-токен — JWT (HS256, секрет из окружения), 15 минут; refresh — httpOnly, SameSite=Strict, 30 дней, ротация.
3. Каждый эндпоинт объявляет требуемое право; проверка — в middleware по матрице прав (документ 2, раздел 8).
4. Лимит частоты: вход — 10 попыток/мин с адреса; остальные — 600 req/мин на пользователя.
5. Вывод пользовательских строк в HTML — только через функцию экранирования; запрет прямого `innerHTML` с данными (правило линтера этапа 2).
6. Журналы не содержат пароли, токены, полные ФИО (только id).
7. Выгрузки не содержат логины/пароли.
8. Заголовки: CSP без `unsafe-inline` (после этапа 1), X-Content-Type-Options, Referrer-Policy.

## 19. Организационные условия

- Владелец продукта: HR-служба (приёмка сценариев согласования).
- Технический лидер: ревью контрактов, безопасности и миграций.
- Инфраструктура: один Linux-стенд (2 vCPU, 4 ГБ) с Docker Compose; бэкап на сетевой ресурс.
- Обучение: 30-минутные инструкции для ролей входят в документ 5.
