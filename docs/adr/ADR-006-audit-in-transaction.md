# ADR-006. Аудит в той же транзакции, что и изменение

Дата: 27.10.2026 · Статус: принято · Решение Р7 документа 1

## Контекст

Журнал «кто что сделал» нужен для споров и разбирательств (кто удалил отпуск, кто согласовал). В прототипе история лежит внутри записи заявки и редактируется клиентом — юридической силы нет.

## Решение

Каждая доменная операция пишет `audit_events` (актор, действие, сущность, before/after) в одной SQLite-транзакции с самим изменением. Таблица append-only: UPDATE/DELETE запрещены на уровне API (их просто нет) и триггером SQLite.

## Последствия

+ Журнал не расходится с данными; сбой записи = сбой изменения (и наоборот — нет «призрачных» событий).
+ Простой экспорт для разбирательств.
− Каждая запись чуть дороже; объём журнала растёт — очистка не предусмотрена (для 500 чел. — тысячи записей в год, нерелевантно).

## Исключения

Чтение не аудируется. Уведомления аудируются фактом создания, не фактом прочтения.
