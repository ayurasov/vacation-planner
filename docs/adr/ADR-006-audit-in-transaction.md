# ADR-006. Аудит в той же транзакции, что и изменение

Дата: 27.10.2026 · Статус: принято · Решение Р7 документа 1 · Актуализировано 29.10.2026 (1.0.0): SQLite заменена PostgreSQL (ADR-010)

## Контекст

Журнал «кто что сделал» нужен для споров и разбирательств (кто удалил отпуск, кто согласовал). В прототипе история лежит внутри записи заявки и редактируется клиентом — юридической силы нет.

## Решение

Каждая доменная операция пишет `audit_events` (актор, действие, сущность, before/after) в одной транзакции PostgreSQL с самим изменением (`prisma.$transaction`, AGENTS.md). Таблица только пополняется: операций изменения и удаления записей журнала в API и в коде сервера нет, задача сроков хранения (1.0.0) журнал не трогает. Триггера в БД нет: задуманный триггер SQLite при переходе на PostgreSQL не переносился.

## Последствия

+ Журнал не расходится с данными; сбой записи = сбой изменения (и наоборот — нет «призрачных» событий).
+ Простой экспорт для разбирательств.
− Каждая запись чуть дороже; объём журнала растёт — очистка не предусмотрена (для 2000 сотрудников — десятки тысяч записей в год, единицы мегабайт; `docs/performance/report-v1.0.0.md`, «Рост данных»).
− Защита от изменения журнала — на уровне программы: администратор СУБД может изменить записи. Если организации нужна защита и от него — отдельная роль БД для API без прав `UPDATE`/`DELETE` на `audit_events` (критерий пересмотра).

Проверка: в 1.0.0 найдено и исправлено нарушение — правила организации и их запись в журнал выполнялись разными транзакциями (`docs/security/assessment-v1.0.0.md`, F-9).

## Исключения

Чтение не аудируется. Уведомления аудируются фактом создания, не фактом прочтения.
