# ADR-012. Кластер процессов и общее состояние только в PostgreSQL

Дата: 30.10.2026 · Статус: принято · v0.5.0 (E40-02, E40-05)

## Контекст

Нагрузочный прогон 500 одновременных пользователей (5000 в базе) на v0.4.0 дал 66 запросов в секунду, p95 чтения 9,2 с и 500 ошибок: Node.js обслуживает запросы одним ядром, а хеширование паролей scrypt и сборка графика занимали его целиком. Ограничение частоты входа хранилось в памяти процесса, поэтому второй процесс или экземпляр давал злоумышленнику вдвое больше попыток.

## Решение

1. `server` запускает `WEB_CONCURRENCY` процессов (`node:cluster`, `auto` — по числу ядер); главный процесс перезапускает упавшие.
2. Всё, что должно быть общим для процессов и экземпляров, хранится в PostgreSQL: окна лимита входа (`login_attempts`, нежурналируемая таблица), версия данных графика (`data_version`, 16 строк-счётчиков, триггеры), очередь писем (`email_outbox`, `FOR UPDATE SKIP LOCKED`), отметки фоновых задач (`job_runs`).
3. Кэш ответов графика — в памяти процесса, но ключ включает версию данных: устаревший ответ не отдаётся ни одним процессом.
4. Пул соединений на процесс ограничивается (`infra/concurrency.ts`), чтобы `WEB_CONCURRENCY=auto` не исчерпывал `max_connections`.

## Последствия

+ 500 одновременных пользователей: 170 запросов в секунду, p95 чтения 159 мс, записи 252 мс, 0 ошибок на 4 ядрах (документ `docs/progress/load-v0.5.0.md`).
+ Нет второго хранилища (Redis): меньше компонентов в поставке, резервном копировании и SBOM.
− Каждый вход — два запроса к БД (окно лимита); каждое изменение графика — обновление строки счётчика (16 строк снимают конкуренцию).
− Метрики процессов собираются через IPC главного процесса (`infra/metrics.ts`).

## Критерии пересмотра

Больше 20 000 пользователей или несколько площадок — Redis или брокер для лимитов и событий.
