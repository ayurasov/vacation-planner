# ADR-018. Структура компании и обмен — как в «По Делу»

Дата: 30.10.2026 · Статус: принято · v1.1.0 (E70)

## Контекст

До v1.1.0 отделы были плоским списком с уникальными названиями, а согласующим был явный руководитель сотрудника или руководитель его отдела. Компания ведёт задачи в «По Делу» (todo-planner): там структура — дерево подразделений с видами уровней, руководитель определяется правилом по дереву, а структура и сотрудники переносятся файлами `podelu.org-structure` и `podelu.employees`. Цель — будущая связка инструментов: одна структура и одни файлы обмена, без ручной сверки и без изменения API для существующих клиентов.

## Решение

**Дерево.** `departments`: `parent_id` (RESTRICT — нельзя удалить подразделение с вложенными), `kind` (вид уровня), `sort_order`, `external_id`, `org_source`. Название уникально среди соседей без учёта регистра (`UNIQUE (COALESCE(parent_id, 0), lower(name))`). Глубина и виды уровней — настройки организации `org_max_depth` (2–30, по умолчанию 15) и `unit_kinds` (по умолчанию — восемь видов «По Делу»). Проверки дерева (цикл, соседи, глубина, вид) — в `OrgService`; чистая модель `OrgTree` строится одним запросом из `departments`.

**Подпись вместо названия.** Существующий API адресует отдел названием (`dept` в фильтрах и ответах, `/departments/{name}`). Подпись подразделения уникальна в организации: название, у одноимённых — «Отдел — Родитель», а если совпадают и родители — полный путь «А / Б / Отдел». Подпись стала значением `dept` и `deptName`; путь `/departments/{ref}` принимает id или подпись. Организации без одноимённых подразделений не замечают изменения. Фильтр `dept` охватывает поддерево.

**Правило руководителя** — как `org_service.direct_manager` «По Делу»:

1. `reports_to_none` («первое лицо») — руководителя нет, заявки решает администратор;
2. явный `manager_id`;
3. иначе — действующий руководитель своего подразделения, если это не сам сотрудник, а без него — первый вверх по дереву.

Очередь согласования, «подчинённые» (меню, права просмотра карточек и заявок, выгрузка, аналитика, сводка), уведомление о новой заявке и эскалация считаются по этому правилу. Очередь строится условием SQL без загрузки сотрудников: `OrgTree.approvalScope` возвращает подразделения, где сотрудники без явного руководителя подчиняются этим руководителям, и руководителей подразделений, подчинённых им по структуре. Право решения шире очереди: руководители своего и вышестоящих подразделений, но не ниже подразделения, которым руководит сам сотрудник (`decidersFor`) — обобщение прежнего права руководителя отдела.

**Обмен.** Форматы «По Делу» версии 1 без изменений:

- структура — `{format, version, exportedAt, app, settings{org_unit_kinds, org_max_depth}, departments[{key, name, parent, kind, sortOrder, externalId, heads[{email, primary}]}]}`, родители раньше вложенных; загрузка сопоставляет по пути от корня, ничего не удаляет, не переименовывает и не переносит;
- сотрудники — CSV (`;`, BOM, CRLF) со столбцами «По Делу» и JSON `podelu.employees`; поля отпусков — объект `vacation` в JSON и столбцы «Табельный номер», «Норма дней», «Перенос», «Тип занятости» в конце CSV (их «По Делу» пропускает). Загрузка — план без записи, коллизии (значение планировщика по умолчанию, файла, объединение, своё), применение одной транзакцией с аудитом каждой записи;
- быстрый импорт CSV — тот же план, но файл главнее.

Соответствие полей: `role` «По Делу» `admin | manager | user` ↔ `is_admin` и `role`; полномочия `org.manage`, `users.manage` ↔ кадровая служба (`is_hr`); «Внешний ID» ↔ `external_id`; «Табельный номер» ↔ `personnel_number` (у «По Делу» это синоним внешнего ID — при совместном экспорте столбец «Внешний ID» идёт раньше и выигрывает). Сотрудник сопоставляется по email, затем по логину и табельному номеру — у планировщика email необязателен. Явный руководитель записывается, только если отличается от руководителя по структуре.

## Отступления от «По Делу»

- Один руководитель у подразделения: дополнительные руководители (`manager_departments`) в плане отмечаются «не переносится».
- Функциональные руководители, часовой пояс, видимость и способ входа выгружаются пустыми и при загрузке пропускаются — в планировщике их нет.
- Новые сотрудники получают одноразовые пароли (в «По Делу» — без пароля до выдачи доступа): вход в планировщик — по паролю или единому входу.
- Синхронизация с AD — не в v1.1.0: нужна зависимость LDAP; быстрый импорт CSV покрывает выгрузку из AD файлом.

## Альтернативы

- Отдельная таблица путей (closure table) — для сотен подразделений дерево в памяти дешевле и проще; запрос подразделений — одна выборка на запрос.
- Сделать идентификатором в API id, а не подпись, — сломало бы фильтры и закладки клиентов v1.0.
- Собственный формат обмена — противоречит цели единообразия; версия формата «По Делу» проверяется при загрузке.

## Последствия

+ Структура переносится между инструментами файлами; правило руководителя совпадает — согласующий в планировщике тот же, кому сотрудник подчиняется в «По Делу».
+ Перевод сотрудника и смена руководителя подразделения больше не требуют правки карточек сотрудников без явного руководителя.
− Каждый запрос очереди, подчинённых и выгрузок читает подразделения (сотни строк) — дополнительная лёгкая выборка; нагрузочный прогон CI проверяет пороги.
− Сотрудники подразделения без явного руководителя стали «подчинёнными» его руководителя (раньше — только очередь): руководитель видит их карточки и заявки.

## Критерии пересмотра

Несколько руководителей у подразделения или функциональное подчинение в планировщике; тысячи подразделений — кэш дерева по версии данных (`data_version` уже меняется при изменении `departments`).
