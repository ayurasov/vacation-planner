# ADR-009. NestJS как серверный каркас

Дата: 27.10.2026 · Статус: принято · Заменяет часть ADR-001 · Решение Р1 документа 1 (v2.0)

## Контекст

Масштаб 1000→5000 пользователей, команда небольшая + ИИ-ассистенты, потребность в корпоративной структуре (DI, guards, валидация, OpenAPI) и предсказуемых правилах для ассистентов. Альтернативы: Fastify «своими руками» (дёшево стартует, дорого сопровождается), NestJS 11, микросервисы.

## Решение

Модульный монолит на NestJS 11 + TypeScript strict. Домены — модули `src/<домен>/`; глобальная аутентификация через APP_GUARD с `@Public()`-исключениями; DTO на class-validator; Swagger из декораторов (`/api/docs`) сверяется с контрактом `contracts/`.

## Последствия

+ Стандартная структура снижает цену входа ассистентов и новых разработчиков; guards/пайпы/фильтры закрывают сквозные задачи.
+ Один язык (TS) на клиенте и сервере; общие типы контракта.
− Декораторная магия требует strict TS и дисциплины DI (type-only импорты ломают метаданные — зафиксировано в AGENTS.md).

## Критерии пересмотра

Появление второго домена с другой моделью нагрузки (массовые рассылки) — выделение worker-процесса, каркас сохраняется.
