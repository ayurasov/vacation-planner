# ADR-004. SQLite на этапе 1 и критерии перехода на PostgreSQL

Дата: 27.10.2026 · Статус: принято · Решение Р2 документа 1

## Контекст

Нагрузка внутреннего инструмента: ~500 пользователей, пики старта рабочего дня, десятки запросов в секунду, writes — десятки в минуту. Эксплуатация без DBA. Прототип уже на SQLite (better-sqlite3, WAL).

## Решение

Остаёмся на SQLite (WAL, `busy_timeout=5000`) на этапах 1–2. Весь доступ к БД — через слой репозиториев без SQLite-специфики в SQL (без CTE/оконных функций, JSON1 только в изолированных хелперах). Переход на PostgreSQL — по измеримым критериям, а не «на всякий случай».

## Критерии перехода (любой из)

1. p95 записи устойчиво > 200 мс при `busy_timeout`-ожиданиях в логах.
2. Появляется второй процесс, пишущий в БД (worker рассылок этапа 2 — если не выделен отдельно).
3. Объём данных > 5 ГБ или бэкап/восстановление перестают укладываться в RTO 1 ч.
4. Требование отказоустойчивости выше одного хоста (репликация).

## Последствия

+ Нулевое администрирование, транзакции «изменение + аудит» тривиальны, бэкап — файл.
− Один писатель (WAL снимает большую часть боли, но не всю); нет сетевого доступа к БД.
− SQL-диалект придётся держать переносимым — дисциплина в репозиториях.

## Миграция при переходе

Отдельная задача: pgloader-скрипт + прогон тестов на двух драйверах; контракт API не меняется.
