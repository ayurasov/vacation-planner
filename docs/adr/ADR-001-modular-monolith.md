# ADR-001. Модульный монолит вместо микросервисов

Дата: 27.10.2026 · Статус: принято · Решение Р1 документа 1 · Каркас уточнён ADR-009 · Актуализировано 29.10.2026 (1.0.0): реализация приведена к NestJS и PostgreSQL, решение не менялось

## Контекст

500 пользователей, пики — десятки запросов в секунду; один бизнес-домен (отпуска); команда 2–3 разработчика с ИИ-ассистентами; эксплуатация — один стенд без выделенной SRE-роли.

## Решение

Один сервис API: NestJS 11 (ADR-009), доменные модули `server/src/<домен>/`; границы модулей — каталоги, модули NestJS и правила импортов, а не процессы. С v0.5.0 сервис запускается кластером одинаковых процессов, общее состояние — только в PostgreSQL (ADR-012); это масштабирование одного монолита, а не выделение сервисов.

## Последствия

+ Простые развёртывание, отладка, транзакции (изменение и журнал изменений в одной транзакции PostgreSQL, ADR-006).
+ Дешёвая разработка с ассистентами: один репозиторий, один контекст.
− Границы держатся дисциплиной кода (правила в AGENTS.md; контроль — ревью).
− Перегрузить один модуль — значит перегрузить всё; мониторинг по процессу, не по модулям.

## Критерии пересмотра

Появление второго домена с другой моделью нагрузки или рост команды выше 6 — вернуться к выделению процессов.

Проверка в 1.0.0: рассылка писем и плановые задачи остались в процессах API (ADR-017) — после исправления разбора очереди она укладывается в требования; тяжёлая выгрузка формы Т-7 вынесена в поток `worker_threads` того же процесса, а не в отдельный сервис. Нагрузочные испытания (`docs/performance/report-v1.0.0.md`): монолит на 1 vCPU обслуживает 2000 сотрудников — повода выделять процессы нет.
