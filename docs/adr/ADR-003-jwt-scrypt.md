# ADR-003. JWT-сессии и пароли scrypt

Дата: 27.10.2026 · Статус: принято · Решение Р4+Р5 документа 1

## Контекст

Сегодня пароли лежат открытым текстом и проверяются на клиенте; сессия — подделываемый `{uid}` в localStorage; API анонимен. Для внутреннего инструмента на 500 человек нужен уровень «принимается ИБ» без enterprise-инфраструктуры.

## Решение

- Пароли: `crypto.scrypt` (N=16384, r=8, p=1) с 16-байтной солью; сравнение `timingSafeEqual`; формат `scrypt$<params>$<salt>$<hash>`.
- Сессия: access JWT (HS256, 15 мин, только id и версия пароля) + refresh в httpOnly SameSite=Strict cookie (30 дней, ротация при каждом обновлении). Смена пароля инкрементирует версию → все access-токены умирают.

## Последствия

+ Ноль новых зависимостей для хеширования; stateless-проверка access.
+ Отзыв сессий через короткий TTL и версию пароля; refresh отзывается точечно.
− Без блэклиста access живёт до 15 минут после «выхода на всех устройствах» — приемлемо для внутреннего инструмента.
− HS256 требует общего секрета — при появлении второго сервиса перейти на RS256 (критерий пересмотра).

## Альтернативы

argon2id — лучше по памяти, но native-зависимость; серверные сессии в БД — проще отзыв, но state и лишние запросы.

## Критерии пересмотра

SSO/OIDC этапа 3; появление второго доверенного сервиса; требования ИБ к блэклисту токенов.
