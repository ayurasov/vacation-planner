# ADR-017. Плановые задачи — в каждом процессе, идемпотентность — в PostgreSQL

Дата: 31.10.2026 · Статус: принято · v0.6.0 (E60, E61, E62)

## Контекст

v0.6.0 добавляет задачи по времени: извещение о начале отпуска за две недели, эскалация заявок без решения, напоминание о планировании, очистка журнала входов. Сервер работает кластером процессов и несколькими экземплярами (ADR-012); выделенного планировщика (cron-контейнера, очереди) в поставке нет.

## Решение

`JobsService` в каждом процессе раз в `JOBS_POLL_SECONDS` (по умолчанию 60) проходит зарегистрированные задачи. Повтор безопасен за счёт БД, а не за счёт выбора «главного» процесса:

- ежедневные задачи захватывают строку `job_runs (задача, дата по времени организации)` через `INSERT … ON CONFLICT DO NOTHING` — выполняет тот, кому досталась строка;
- извещение — уникальный ключ `(заявка, дата начала)`: второй процесс получает `ON CONFLICT DO NOTHING` и не уведомляет;
- эскалация — `UPDATE … WHERE escalated_at IS NULL` перед уведомлением;
- автоматическое напоминание о планировании — `UPDATE … SET auto_reminded = true WHERE NOT auto_reminded` в той же транзакции, что и рассылка.

Ошибка одной задачи не останавливает остальные; тесты отключают таймер (`JOBS_POLL_SECONDS=0`) и вызывают задачи напрямую.

## Альтернативы

- Отдельный контейнер-планировщик — лишний компонент и ещё одна точка отказа.
- Advisory lock «лидера» — при падении лидера задачи ждут переизбрания; идемпотентность всё равно нужна на случай повтора после сбоя.

## Последствия

+ Задачи работают при любом числе процессов и экземпляров, переживают перезапуски, не дублируют уведомлений.
− Каждый процесс делает несколько лёгких запросов в минуту впустую; нагрузочный прогон v0.6.0 это учитывает.

## Критерии пересмотра

Тяжёлые задачи (минуты процессорного времени) — вынос в отдельный рабочий процесс с очередью в PostgreSQL.
